# My firmware (step 5)

*Started 2026-10-20. I asked for everything to keep moving without stopping to ask, so I made these calls myself and wrote down why. Like everything here, it changes once real numbers show up.*

## What this step has to produce

From the [roadmap](../roadmap.md): my own flight code and the safety monitor's, passing the same tests as PX4. The architecture was set back in the plan: flight logic separate from the hardware drivers, so the same code runs in the sim and on the ARK FPV's STM32H743; a hardware watchdog and fresh DShot frames every loop, so a hung CPU means the motors stop; flight modes as separate pieces on one controller; and a landing sequence with a swappable descent part, so the spiral descent drops in later. Earlier steps added requirements: the 90 A current cap with its XT60 heat limit (step 3d), the safety monitor holding each DShot line high between its stop frames after a takeover (step 3's switch sims), the parachute rule, and a tuning profile per module combination.

**Done when:** my firmware and the safety monitor pass the same tests as PX4, in all eight combinations.

## Decided

**The language (2026-10-20): C++17.** The same code builds for my PC (the sim and the tests), the STM32H743 (with arm-none-eabi-gcc) and the Teensy 4.1. dRehmFlight, the roadmap's warm-up, is C++, and so is most of the flight code I'll read to learn from. **Why:** one language on all three targets and the most to learn from. **Cost:** it's easier to write memory bugs in C++ than in Rust; the host tests run with sanitizers to catch them early.

**The shape (2026-10-20): one core library, thin platform layers.** `firmware/core` holds everything that decides anything: the estimator, the controllers, the mixer, the modes, the failsafes, the limits profile, the current cap and its heat limit. It has no hardware in it and is tested on my PC. Around it:
- `firmware/sitl`: the core as a Linux program that talks to Gazebo, standing in for PX4's Gazebo bridge: sensors in, motor speeds out
- `firmware/h743`: the ARK FPV's drivers, later in the step (the IMU on SPI, DShot by timer DMA, the CRSF receiver, DroneCAN for the GPS, the SD card)
- `firmware/monitor`: the safety monitor, its own core and its own Teensy layer

**Why:** the sim and the drone run the same decisions, and the tests don't need either. **Cost:** a platform layer per target to keep in step with the core.

**Speaking PX4's language (2026-10-20): MAVLink, PX4's dialect, and ULog.** My firmware identifies itself the way PX4 does and answers the commands and streams the flight sim's scripts use (arming, takeoff, land, return, hold, offboard setpoints, manual sticks, parameters, failure injection), and it writes its log as ULog with the topics the graders read. Then the same scenario scripts fly it and the same graders grade it, which makes "passing the same tests as PX4" literal. QGroundControl works with it for free. **Why:** no second test harness, and a direct comparison. **Cost:** a MAVLink subset and a ULog writer to build, and the discipline to match PX4's behavior where the scripts depend on it. MAVLink's generated C headers are MIT-licensed, fine next to GPL-3.0.

**Starting from (2026-10-20): my own code, reading PX4's and dRehmFlight's.** PX4 is BSD-licensed and dRehmFlight GPL-3.0, so borrowing from either is allowed; the point is to learn, so the code is mine, and anything adapted says where it came from.

**The order (2026-10-20):** the roadmap's, rate mode first. Each mode flies in the sim before the next one starts: rate, then self-level, then altitude hold, then position, then the automatic modes the scenarios use. The failsafes and limits come with the modes that need them.

**The estimator (2026-10-20): simple first.** A complementary attitude filter (Mahony's), then a small Kalman filter for height (barometer and accelerometer) and one for position (GPS and accelerometer). An EKF like PX4's comes only if the scenarios show these aren't enough. **Why:** I can understand and debug them; the learning file gets the theory.

**The safety monitor (2026-10-20): its own program from day one.** Its core reads its own IMU and the receiver's feed, watches the flight controller's heartbeat, runs the reference triggers from step 4 (`pcs14.safety.triggers`) in shadow mode, and owns the motor cut and the takeover's line holding. In the sim it gets its own simulated IMU from Gazebo, separate from the flight controller's. Its triggers have to give the same answers as the Python reference on the same recorded data.

**The ground station (2026-10-20): QGroundControl first, my own later.** Because the firmware speaks MAVLink, QGroundControl gives live telemetry and parameters on day one. My own ground station (live PID tuning and the active limits profile always on screen) comes after the modes fly.
