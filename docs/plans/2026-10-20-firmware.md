# Implementation plan: my firmware

*Written 2026-10-20, from the [firmware spec](../specs/2026-10-20-firmware.md). Test-first, like every step.*

## Where things go

| What | Where |
|---|---|
| The core: math, estimator, controllers, mixer, modes, failsafes, limits, current cap | `firmware/core/` (C++17, no hardware), tests in `firmware/core/tests/` |
| The sim layer, standing in for PX4's Gazebo bridge | `firmware/sitl/`, built inside WSL2 against Gazebo Harmonic |
| The ARK FPV layer | `firmware/h743/` |
| The safety monitor | `firmware/monitor/` (its core and its Teensy layer) |
| Build | CMake; the host build runs in CI on every push |
| Running the flight sim's scenarios on it | `pcs14 flight-sim run --firmware mine` |

## The tasks

| # | Task | What the tests check |
|---|---|---|
| 1 | **The tree and the build:** CMake, doctest for the host tests, a CI job that builds and tests the core with sanitizers | A trivial core test passes in CI |
| 2 | **Math and the attitude estimator:** vectors, quaternions, Mahony's complementary filter | Hand-worked rotations; a still IMU settles to level; a steady turn tracks within a degree |
| 3 | **Rate control and the mixer:** a PID per axis (derivative on the gyro, low-pass filters, output limits, integrator clamping), the quad X mixer from the generator's rotor geometry, and motor commands mapped like PX4's (idle to top speed) | Step responses on a modeled axis; the mixer's columns against PX4's for the same geometry; saturation keeps attitude over thrust |
| 4 | **The sim layer:** a Gazebo node reading the model's IMU, barometer, magnetometer and GPS and the clock, and sending the four motor speeds; spawning the model the way PX4 does | Rate mode holds the drone level-ish on the sticks in Gazebo for 10 s |
| 5 | **The ULog writer:** the topics the graders read (ground truth, motors, IMU, status, landed state, failsafe flags, battery) | pyulog reads a written file back exactly |
| 6 | **MAVLink, PX4's dialect:** heartbeat with PX4's mode encoding, the streams MAVSDK listens to (IMU, attitude, position, home, landed state, health, battery), commands with acks (arm, takeoff, land, return, mode changes, failure injection, termination, message rates), offboard setpoints, manual sticks, parameters | MAVSDK connects, reads health and arms against the sim |
| 7 | **Self-level and altitude hold:** angle control on the sticks, a height filter (barometer and accelerometer), a thrust loop | The steps scenario in altitude mode; a hover holds height |
| 8 | **Position and the automatic modes:** a position filter (GPS and accelerometer), position and velocity loops, takeoff, hold, land, return, offboard | The smoke and hover scenarios pass |
| 9 | **Failsafes and limits:** lost link, low battery counted in mAh, the geofence, the limits profile, the current cap with the XT60 heat limit, the parachute rule, the kill switch, an attitude failure detector that terminates and fires the chute | The lost link, low battery, dead motor and drop scenarios |
| 10 | **The safety monitor:** its core (heartbeat watch, kill switch, the reference triggers in shadow mode, the takeover's line holding), its own simulated IMU | Its triggers match `pcs14.safety.triggers` on the same recorded data; a killed heartbeat cuts in the sim |
| 11 | **Every scenario on my firmware:** all twelve, in all eight combinations, graded the same way and laid over PX4's | The baseline passes what PX4 passes, or the report says why not |
| 12 | **The ARK FPV layer:** drivers against ARK's pinout, built for the H743 in CI, tested with fakes on the host | It builds; the drivers' logic passes against recorded or made-up bus data |
| 13 | **Ground station v1:** live telemetry, live PID tuning, the active limits profile on screen | Talks to the sim's firmware |

Tasks 1 to 3 and 5 need only my PC; 4 and 6 to 11 need WSL2 and Gazebo; 12 needs the ARM toolchain.

**Done when:** my firmware and the safety monitor pass the same tests as PX4.

## Notes for task 6, from MAVSDK's source

What MAVSDK v3.17.4 (the one the flight sim pins) needs from an autopilot, read from its telemetry plugin (`src/mavsdk/plugins/telemetry/telemetry_impl.cpp` at the v3.17.4 tag):

| What the runner asks for | Where MAVSDK gets it |
|---|---|
| Connected | HEARTBEAT, from system 1, component 1, with PX4 as the autopilot (12) and PX4's mode encoding in custom_mode |
| Armed, flight mode | HEARTBEAT's base_mode (the armed flag) and custom_mode |
| IMU, and the runner's clock | HIGHRES_IMU's time_usec, at the rate asked with MAV_CMD_SET_MESSAGE_INTERVAL |
| Position and velocity | LOCAL_POSITION_NED |
| Global position ok, local position ok | SYS_STATUS: the GPS sensor bit present, enabled and healthy |
| Home position ok | HOME_POSITION |
| Armable | SYS_STATUS: the pre-arm check bit healthy |
| Landed state, in air | EXTENDED_SYS_STATE |
| Battery | BATTERY_STATUS, or SYS_STATUS's battery fields until one arrives |
| Parameters | PARAM_SET answered by PARAM_VALUE |
| Commands | COMMAND_LONG answered by COMMAND_ACK: arm, takeoff, land, return, mode changes, termination, failure injection, message intervals |
| Offboard and sticks | SET_POSITION_TARGET_LOCAL_NED and MANUAL_CONTROL |

Two PX4 habits MAVSDK leans on: it sets the take-off height as the parameter MIS_TAKEOFF_ALT and sends NAV_TAKEOFF with no height, and it changes modes with MAV_CMD_DO_SET_MODE carrying PX4's main and sub mode (`src/mavsdk/core/px4_custom_mode.h`). So the parameter store is real from task 6 on, not a stub.

The C headers: mavlink/c_library_v2 at commit 8c63a49fe35aead7f9ef14031381c5e076ff743a (generated 2026-10-12), whose archive's SHA256 is c192167675c9022b6382942c3a31eb1f89452e0bbcd9581105504cf2bff871e9. MAVLink's generated C library is MIT-licensed.
